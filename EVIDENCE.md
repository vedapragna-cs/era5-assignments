## 9. Checkpoint, crash, resume, replay

Checkpoints carry weights, optimizer moments, step count, data cursors, RNG state, ledger offsets and the binding hashes of the data they were trained on.

| checkpoints | all verify | corruption flavours tested | all detected |
|---|---|---|---|
| 3 | True | 3 | True |

| induced corruption | detected | how |
|---|---|---|
| truncated_weights | True | weights hash mismatch: state.pt is truncated or rewritten |
| truncated_meta | True | meta.json unparseable: Unterminated string starting at: line 1 column 888 (char 887) |
| missing_rng | True | missing rng.json |

Writes go to <file>.tmp, are fsynced, then os.replace()d. os.replace is atomic within a filesystem, so a real crash leaves either the whole old checkpoint or the whole new one. These corruptions are induced after the fact to prove the verifier would catch the case anyway.

**Crash and resume.** A checkpoint is saved, training continues, the run state is destroyed, and the run is rebuilt from the checkpoint and re-trained over the same steps. Bitwise weight equality is the claim; ledger row equality is the proof it was the same data in the same order.

| checkpoint at | crash at | ledger rows on disk | orphan rows repaired | weights identical | ledger identical | totals match |
|---|---|---|---|---|---|---|
| 34 | 38 | 38 | 4 | True | True | True |

The orphan rows are the point. The ledger was appended to for every step up to the crash; the weights only got as far as the checkpoint. A resume that keeps those rows claims the model consumed tokens it has never seen -- in the one artifact whose entire purpose is to be believed.

**Replay.** Batches regenerated from the ledger's recorded cursor state, then compared on batch id, token spans and content hash. The ledger is the source of truth; the code is only asked to agree with it.

| steps replayed | matching | all match |
|---|---|---|
| 5 | 5 | True |
